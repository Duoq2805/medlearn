1) Tổng quan kiến trúc Disease

Core philosophy: Disease content là versioned asset, không overwrite trực tiếp approved content.

  • Metadata layer: Disease (name, slug, category, pointer currentVersion).
  • Content layer: DiseaseVersion + DiseaseSection + DiseaseVersionSymptom.
  • Workflow layer: DRAFT → PENDING_REVIEW → APPROVED / REJECTED → ARCHIVED.
  • Governance layer: role-based moderation (REVIEWER/ADMIN) + ownership checks.
  • Persistence pattern: soft delete + optimistic lock; high-value transitions dùng pessimistic lock.

Why design như vậy: đảm bảo traceability + moderation integrity + immutable public content, phù hợp platform học thuật (không clinical system).

2) Domain Model chi tiết

2.1 Disease

Entity: Disease
Table: disease
Key fields:
- id (PK)
- name (unique)
- slug (unique, NaturalId)
- category (ManyToOne)
- currentVersion (OneToOne -> DiseaseVersion)
- versions (OneToMany -> DiseaseVersion)
- deletedAt (soft delete)
- version (optimistic lock)
  • Meaning: container metadata + con trỏ nội dung public hiện tại.
  • Invariant: currentVersion == null || currentVersion.status == APPROVED.

2.2 DiseaseVersion

Entity: DiseaseVersion
Table: disease_version
Unique: (disease_id, version_number)
Key fields:
- disease (ManyToOne)
- versionNumber (per disease sequence)
- createdBy (ManyToOne User)
- status (VersionStatus)
- moderationNote
- reviewedBy, reviewedAt
- sections (OneToMany DiseaseSection, orphanRemoval)
- symptoms (OneToMany DiseaseVersionSymptom, orphanRemoval)
- deletedAt
- version (optimistic lock)
  • Meaning: snapshot nội dung theo vòng đời moderation.
  • Invariant: approved content chỉ thay bằng version mới, không edit trực tiếp.

2.3 DiseaseSection

Entity: DiseaseSection
Table: disease_section
Key fields:
- diseaseVersion (ManyToOne)
- sectionType (ManyToOne SectionType)
- title
- content (TEXT, sanitized by service)
- orderIndex
- deletedAt
  • Meaning: khối nội dung có thứ tự hiển thị trong 1 version.
  • Invariant: edit chỉ khi version ở DRAFT.

2.4 DiseaseVersionSymptom

Entity: DiseaseVersionSymptom
Table: disease_version_symptom
Unique: (disease_version_id, symptom_id)
Key fields:
- diseaseVersion (ManyToOne)
- symptom (ManyToOne)
- weightScore (default 1.0)
  • Meaning: mapping symptom cho version + scoring cho symptom checker.

5) Version Lifecycle

5.1 Effective lifecycle

DRAFT -> PENDING_REVIEW -> APPROVED -> ARCHIVED
                         \-> REJECTED -> (DRAFT or ARCHIVED)

Transitions theo VersionStatus.canTransitionTo().

5.2 Current version policy

  • Public reads dựa vào Disease.currentVersion.
  • Approve mới: archive old APPROVED versions + set pointer mới.
  • Rollback: tạo snapshot APPROVED mới từ target APPROVED cũ, không tái dùng row cũ.

8) Service Layer Deep Dive

8.1 DiseaseServiceImpl

createDisease(CreateDiseaseRequest)

  • Purpose: tạo Disease metadata + bootstrap draft version #1.
  • Workflow: validate name/slug → resolve category → save disease → call diseaseVersionService.createDraftVersion().
  • Validation: duplicate name/slug; missing category.
  • Permission: endpoint cho USER/REVIEWER/ADMIN.
  • Exceptions: IllegalStateException, ResourceNotFoundException.
  • Side effects: insert disease + insert version draft.
  • Dependencies: DiseaseRepository, CategoryRepository, DiseaseVersionService, DiseaseMapper.

updateDiseaseMetadata(Long, UpdateDiseaseRequest)

  • Purpose: chỉnh metadata (name/slug/category), không đụng content.
  • Workflow: load disease → ownership/privileged check → validate unique → save.
  • Validation: uniqueness, category existence.
  • Permission: owner hoặc REVIEWER/ADMIN.
  • Exceptions: not found, duplicate, unauthorized owner.
  • Side effects: update searchable identity fields.
  • Dependencies: DiseaseRepository, DiseaseVersionRepository, UserRepository.

cloneCurrentVersion(Long)

  • Purpose: mở nhánh chỉnh sửa mới từ approved hiện tại.
  • Workflow: delegate diseaseVersionService.cloneApprovedVersion.
  • Validation: approved current version must exist.
  • Permission: endpoint role + ownership logic inside version service.
  • Exceptions: current approved not found.
  • Side effects: new DRAFT with deep-cloned sections/symptoms.
  • Dependencies: DiseaseVersionService.

validateDiseaseOwnership(Long)

  • Purpose: guard write operations against non-owner contributor.
  • Workflow: privileged role bypass → otherwise check existence of any version created by current user.
  • Validation: disease exists, user exists.
  • Permission: contributor must be historical owner.
  • Exceptions: not found, not owner.
  • Side effects: none.
  • Dependencies: DiseaseRepository, DiseaseVersionRepository, CurrentUserResolver, UserRepository.

8.2 DiseaseVersionServiceImpl

createDraftVersion(Long, CreateDiseaseVersionRequest)

  • Purpose: tạo draft rỗng (hoặc note) cho disease.
  • Workflow: load disease + user → compute next version number → save DRAFT.
  • Validation: disease exists.
  • Permission: caller path kiểm soát qua controller/service flow.
  • Exceptions: disease/user not found.
  • Side effects: increments version lineage.
  • Dependencies: DiseaseRepository, DiseaseVersionRepository, UserRepository.

cloneApprovedVersion(Long)

  • Purpose: preserve immutable approved content while enabling edits.
  • Workflow: load current approved → create new draft → clone sections → clone symptoms.
  • Validation: current version exists and status APPROVED.
  • Permission: called from authenticated write path.
  • Exceptions: approved not found / invalid status.
  • Side effects: many inserts in section/symptom tables.
  • Dependencies: DiseaseVersionRepository, DiseaseSectionRepository, DiseaseVersionSymptomRepository.

submitForReview(Long)

  • Purpose: chuyển draft sang moderation queue.
  • Workflow: load version → validate transition DRAFT→PENDING_REVIEW → validate ownership → set status.
  • Validation: transition + ownership.
  • Permission: owner or privileged role.
  • Exceptions: invalid transition / not owner.
  • Side effects: status update.
  • Dependencies: DiseaseVersionRepository, CurrentUserResolver, UserRepository.

approveVersion(Long, ModerationRequest)

  • Purpose: publish version atomically.
  • Workflow: validate reviewer role → load version → validate transition → block self-approve → lock disease row → archive old approved → mark approved + review metadata → set currentVersion → save.
  • Validation: role, transition, reviewer != creator.
  • Permission: REVIEWER/ADMIN only.
  • Exceptions: unauthorized, invalid transition, self-approve, not found.
  • Side effects: changes multiple rows/statuses + pointer switch.
  • Dependencies: DiseaseRepository.findByIdForUpdate(), DiseaseVersionRepository.archiveApprovedVersionsExcept().

rejectVersion(Long, ModerationRequest)

  • Purpose: moderation reject with reviewer trace.
  • Workflow: validate reviewer role + transition → set REJECTED + note + reviewedAt/by.
  • Validation: role + PENDING_REVIEW→REJECTED.
  • Permission: REVIEWER/ADMIN only.
  • Exceptions: unauthorized, invalid transition, not found.
  • Side effects: version out of active edit flow unless transitioned back to draft later.
  • Dependencies: DiseaseVersionRepository, UserRepository.

archiveVersion(Long)

  • Purpose: manually archive non-active version.
  • Workflow: validate reviewer role + transition → set ARCHIVED.
  • Validation: canTransitionTo(ARCHIVED).
  • Permission: REVIEWER/ADMIN only.
  • Exceptions: unauthorized / invalid transition.
  • Side effects: removes version from active lifecycle.
  • Dependencies: DiseaseVersionRepository.

validateVersionOwnership(Long) / validateReviewerPermission()

  • Purpose: centralized authorization checks.
  • Workflow: role lookup from user roles; privileged bypass for ownership.
  • Validation: current user exists with roles.
  • Permission: enforce contributor-vs-moderator boundaries.
  • Exceptions: unauthorized/not owner/user not found.
  • Side effects: none.
  • Dependencies: CurrentUserResolver + UserRepository.

generateNextVersionNumber(Long)

  • Purpose: compute next sequence.
  • Workflow: query max(versionNumber) then +1; fallback 1.
  • Validation: none explicit.
  • Permission: internal helper.
  • Exceptions: none (DB failure excepted).
  • Side effects: none itself.
  • Dependencies: DiseaseVersionRepository.findMaxVersionNumberByDiseaseId().

8.3 DiseaseSectionServiceImpl

createSection / updateSection / deleteSection / reorderSections

  • Purpose: mutate draft content blocks.
  • Workflow: load version/section → validateVersionEditable(DRAFT + owner/privileged) → sanitize content → persist.
  • Validation: version exists, section belongs to version, section type exists.
  • Permission: owner contributor hoặc REVIEWER/ADMIN.
  • Exceptions: not found, version not draft, section mismatch, not owner.
  • Side effects: soft delete sets deletedAt; reorder impacts render order.
  • Dependencies: DiseaseSectionRepository, DiseaseVersionRepository, SectionTypeRepository, UserRepository.

validateRequiredSections(Long)

  • Purpose: check required section types: definition/symptoms/treatment.
  • Workflow: query section types in version → all required must exist.
  • Validation: strict required-list.
  • Permission: n/a (validation utility).
  • Exceptions: throws if missing.
  • Side effects: none.
  • Dependencies: DiseaseSectionRepository.

sanitizeHtmlContent(String)

  • Purpose: prevent unsafe HTML persistence.
  • Workflow: null→"" else Jsoup.clean(..., Safelist.basic()).
  • Validation: whitelist sanitization.
  • Permission: n/a.
  • Exceptions: none expected.
  • Side effects: strips unsupported tags/attrs; potential content loss if user expects richer HTML.
  • Dependencies: Jsoup.

8.4 DiseaseWorkflowServiceImpl

submit/approve/reject wrappers

  • Purpose: orchestration facade, delegates to DiseaseVersionService.
  • Workflow: simple pass-through under transactional boundary.
  • Validation/Permission: delegated.
  • Exceptions: delegated.
  • Side effects: same as delegated methods.
  • Dependencies: DiseaseVersionService.

rollback(Long diseaseId, Long targetVersionId)

  • Purpose: controlled rollback by snapshot (not pointer rewind).
  • Workflow: reviewer check → lock disease row → validate target belongs + APPROVED → create new APPROVED snapshot with next version number → clone sections/symptoms → archive other approved → set currentVersion.
  • Validation: target ownership, target status, role.
  • Permission: REVIEWER/ADMIN only.
  • Exceptions: disease/version not found; invalid target relation/status.
  • Side effects: inserts new version + clones, archives previous approved, changes public pointer immediately.
  • Dependencies: DiseaseRepository, DiseaseVersionRepository, DiseaseSectionRepository, DiseaseVersionSymptomRepository, CurrentUserResolver, UserRepository.

11) Repository Layer Overview

DiseaseRepository

  • findByIdForUpdate(): pessimistic write lock để serialize approve/rollback pointer update.
  • findBySlugWithCategory(): fetch category cùng disease detail.
  • findApprovedSummaryByFilters()/findSummaryByApprovedFilters(): list/search approved current versions only.

DiseaseVersionRepository

  • findCurrentVersionByDiseaseId(): read qua Disease.currentVersion pointer.
  • findMaxVersionNumberByDiseaseId(): sequence source cho version numbers.
  • archiveApprovedVersionsExcept(): bulk state update để giữ single approved semantics.

DiseaseSectionRepository

  • findAllByDiseaseVersionIdAndDeletedAtIsNullOrderByOrderIndexAsc(): canonical ordered read.
  • findAllByVersionIdWithType(): fetch join sectionType tránh N+1 khi render detail.

DiseaseVersionSymptomRepository

  • CRUD + bulk operations for version symptom mapping.
  • Native query scoring (findMatchingDiseasesRaw) cho symptom checker.
  • Filtering current approved only để align public relevance.

13) Concurrency & Consistency

13.1 Protections hiện có

  • Optimistic lock: @Version ở Disease, DiseaseVersion.
  • Pessimistic lock: DiseaseRepository.findByIdForUpdate() dùng trong approve + rollback.
  • Uniqueness constraints: disease name/slug, version number per disease, symptom mapping unique.
  • Transactional boundaries: state-transition methods annotated @Transactional.

13.2 Known race hotspots

  • generateNextVersionNumber() = max+1 không lock riêng; concurrent draft creation có thể đụng unique constraint.
  • createDisease() checks exists before insert; race giữa requests vẫn có thể chạm DB unique violation.
  • Bulk archive query + pointer update phụ thuộc transaction integrity; split transaction sẽ tạo inconsistent public pointer.

13.3 Invariants bắt buộc giữ

  1. Một disease tại một thời điểm chỉ có một version public qua currentVersion.
  2. Content public phải từ version APPROVED.
  3. Approved content không sửa in-place.
  4. Reviewer không tự duyệt version tự tạo.
  5. Section mutation chỉ diễn ra ở DRAFT version.

14) Security Rules

  • Entry guard: controller @PreAuthorize cho write operations.
  • Domain guard: service-level ownership/role validation; không rely hoàn toàn vào controller.
  • Trust source: user identity từ CurrentUserResolver + DB reload with roles.
  • Moderation boundary: approve/reject/archive/rollback yêu cầu reviewer/admin.
  • XSS mitigation: section content sanitize qua Jsoup safelist.

Security caveat: detail/read endpoints public. Nếu cần content embargo theo role, phải thêm policy layer trước mapper response.

16) Technical Debt

  1. Required sections validation not enforced in submitForReview: method exists nhưng không được gọi trong workflow submit hiện tại.
  2. Duplicate query intent: findApprovedSummaryByFilters và findSummaryByApprovedFilters gần như trùng.
  3. Role strings hardcoded: "REVIEWER"/"ADMIN" lặp lại nhiều chỗ, dễ typo drift.
  4. Manual clone loops: section/symptom cloning duplicated giữa VersionService và WorkflowService.
  5. Potential N+1/transaction chatter: reorder/soft-delete sections save từng row.
  6. Controller coverage gap: workflow services chưa thấy exposed endpoint trong controller đã scan.

17) Next Priorities

  1. Wire validateRequiredSections() vào submitForReview() trước khi mở rộng moderation UI.
  2. Create dedicated workflow controller endpoints (submit/approve/reject/rollback) nếu chưa tồn tại.
  3. Extract authorization helper/policy component để giảm lặp role checks.
  4. Harden concurrent version-number generation (DB sequence/table lock/retry strategy).
  5. Add integration tests cho invariants: single approved pointer, self-approval block, rollback snapshot behavior.
  6. Unify duplicate approved-summary queries để giảm maintenance cost.

18) Developer Recovery Guide

18.1 Nếu bạn quay lại sau nhiều tháng

  1. Đọc section 4, 5, 13 trước: business invariants + lifecycle + concurrency.
  2. Mở DiseaseVersionServiceImpl.approveVersion() và DiseaseWorkflowServiceImpl.rollback() trước mọi thay đổi workflow.
  3. Kiểm tra mọi thay đổi có giữ invariant currentVersion -> APPROVED không.
  4. Nếu sửa permission: update cả controller guard và service guard.
  5. Nếu thêm field content: validate clone path (cloneApprovedVersion + rollback clone methods).
